# v0.1.0 開発概要

## 1. 位置付け

v0.1.0 は、Phase 0 の初期技術検証で個別に成立確認した要素を、実際に利用可能な Workflow IDE Framework の最小構成へ統合する最初の開発版である。

v0.1.0 の目的は「すべての IDE 機能を実装すること」ではない。

アプリケーション開発者が Framework を利用して、Dock 型 IDE の外枠を構築し、その中へ通常 UI、GPU Viewport、Browser Panel を同じ UI モデルの下で配置できる状態を作ることをゴールとする。

## 2. v0.1.0 のゴール

v0.1.0 完了時には、Framework 利用アプリから次の最小 IDE を構築できること。

```text
Application
   |
Workflow IDE Framework
   |
   +-- Window / Custom Title Bar
   +-- Dock / Panel
   |     +-- Standard UI Panel
   |     +-- GPU Viewport Panel
   |     +-- Browser Panel
   |
   +-- Surface
         +-- GPU Surface
         +-- Browser Surface
```

利用アプリは Windows / Linux / macOS の個別 Window API、CEF OSR、wgpu の Dock 接続処理を直接記述しない。

## 3. v0.1.0 でできるようにすること

### 3.1 IDE Window

- Framework から IDE Window を起動できる。
- Dock UI を表示できる。
- 必要な環境では Custom Title Bar を使用できる。
- Embedded Font により日本語 UI を表示できる。

### 3.2 Panel / Dock

- 利用アプリが Panel を定義できる。
- 複数 Panel を Dock 上へ配置できる。
- Panel の Resize が内容へ伝達される。
- 通常の egui UI を Panel 内容として表示できる。

v0.1.0 では「1 tab = 1 area」を前提としない。

### 3.3 GPU Viewport

- 利用アプリが GPU Viewport を Panel として配置できる。
- GPU Viewport の描画結果を GPU Surface 経由で Dock 内へ表示できる。
- Resize / Visibility / Focus / Lifecycle / 基本入力を扱える。
- MuJoCo、VRM Preview、Simulation 等を後続で実装できる境界を持つ。

v0.1.0 自体には MuJoCo や VRM のドメイン実装を含めない。

### 3.4 Browser Panel

- 利用アプリが Browser Panel を Dock 上へ配置できる。
- CEF OSR を Browser Surface の主実装として利用する。
- URL を読み込み、Dock 内で表示・更新できる。
- Pointer / Wheel / Keyboard / Focus / Text / IME を Browser へ渡せる。

Help / Docs / Tutorial / AI Chat 等の実アプリ機能そのものは v0.1.0 の必須成果物としない。

### 3.5 Surface 共通入力

GPU / Browser の双方で共通の入力モデルを利用できるようにする。

対象:

- PointerMove
- PointerButton
- Wheel
- Keyboard
- TextInput
- CompositionStart
- CompositionUpdate
- CompositionCommit
- CompositionEnd
- Focus

文字入力を行う Surface は caret / composition target の位置を Framework へ通知できる。

GPU Surface に IME を必須とはしない。GPU Viewport 内の独自 UI 等が文字入力を必要とするときに共通 IME model を利用できることをゴールとする。

### 3.6 日本語

- Framework renderer 内の日本語表示を Embedded Font で成立させる。
- OS font fallback のみに依存しない。
- Linux Native Window Title の問題を Framework 利用アプリへ露出させず、必要に応じて Custom Title Bar を利用できる。
- Browser Surface の日本語 IME を共通 Surface input model から CEF へ接続できる。
- GPU Viewport 内で文字入力を実装する場合にも同じ IME model を利用可能にする。

P0-2 で記録した Windows Browser Surface の最初の Space に関する Candidate Window 挙動は残課題として追跡する。

## 4. 最初の実利用アプリ

v0.1.0 の最初の実利用アプリは `mayusaki3/meridian-mujoco-runtime` の `develop` ブランチとする。

meridian-mujoco-runtime は MuJoCo を中核とするロボットシミュレーション Runtime であり、将来的に sysid、SIL / HIL、SimToReal / RealToSim、RuntimeSession、実時間 / simulation time 等を扱う。

workflow-ide-framework はこれらのドメイン機能を所有しない。Framework は、それらを IDE 上で表示・操作するための Window / Dock / Panel / Surface / Input の境界を提供する。

責務境界は次を基本とする。

```text
meridian-mujoco-runtime
  ├─ MuJoCo / simulation loop
  ├─ RuntimeSession
  ├─ Robot / Actuator / Field / Scenario
  ├─ sysid / SIL / HIL
  └─ domain state
          |
          | workflow-ide-framework public API
          v
workflow-ide-framework
  ├─ Window
  ├─ Dock / Panel
  ├─ Standard UI
  ├─ GPU Viewport / GPU Surface
  ├─ Browser Panel / Browser Surface
  └─ Input / IME / Lifecycle
```

MuJoCo API や meridian 固有データ型を workflow-ide-framework の公開 API に組み込まない。

### 4.1 利用イメージ

最初の実利用では、最低限次の構成を一つの IDE Window に同時表示できることを目標とする。

```text
+----------------------------------------------------+
| Custom / Native Title                              |
+----------------------+-----------------------------+
| Standard UI Panel    | GPU Viewport                |
|                      |                             |
| 日本語 UI             | dynamic GPU rendering       |
+----------------------+-----------------------------+
| Browser Panel                                      |
| URL display / pointer / keyboard / Japanese IME   |
+----------------------------------------------------+
```

Framework 内部には最小 example / probe を保持してよいが、v0.1.0 の実利用 Acceptance は meridian-mujoco-runtime から Framework を利用して成立することを基準とする。

meridian-mujoco-runtime 側が MuJoCo の simulation / render に必要な状態と更新タイミングを所有し、workflow-ide-framework は GPU Viewport の描画先、Dock 統合、入力、Resize / Visibility / Focus / Lifecycle を提供する構成を第一候補とする。

## 5. v0.1.0 の完了条件

v0.1.0 は以下を満たした時点で完了とする。

1. Framework crate の公開境界から Window / Dock / Panel を構築できる。
2. Standard UI Panel、GPU Viewport Panel、Browser Panel を同一 Window / Dock 内で共存させられる。
3. GPU / Browser が共通 Surface lifecycle / input model を利用する。
4. GPU Surface と Browser Surface の実装固有型を、不要に利用アプリ API へ露出させない。
5. Embedded Font による日本語 UI 表示が成立する。
6. Browser Panel で日本語 IME 入力が可能である。
7. GPU Viewport は共通 IME model を受け取れる設計・実装境界を持つ。実際の GPU 内文字編集 UI は acceptance application で最小確認する。
8. Resize / Visibility / Focus / Create / Close の基本 Lifecycle が Panel / Surface 間で成立する。
9. Windows で meridian-mujoco-runtime を最初の実利用アプリとした integration acceptance を完了する。
10. Linux は利用可能な VM で判定可能な項目を確認する。
11. Linux 実機 / 物理 GPU / macOS 等、環境を用意できない項目は `？` として記録し、非対応とは判定しない。
12. v0.1.0 の公開 API と内部 backend 境界が文書化されている。

## 6. v0.1.0 に含めないもの

以下は将来の v0.x へ送る。

- Workflow Node / Graph 実装
- Event / State 基盤の完成
- Command / Undo / Redo 基盤の完成
- Runtime process 分離
- Remote Runtime
- Plugin Loader / Plugin API
- Workspace / Session の完全な保存・復元
- 本格的な Layout persistence
- MuJoCo / VRM 等のドメイン固有 Viewport
- AI Runtime
- Debugger
- zero-copy / GPU 間 Texture 共有の最適化
- GPU backend ごとの性能最適化
- Accessibility / Drag and Drop / Clipboard の完全対応

ただし、将来追加するために必要な拡張点を v0.1.0 API が不必要に閉じないことは要求する。

## 7. API 設計へ与える制約

詳細 API は上記ゴールから逆算する。

### 7.1 Application API と Backend API を分離する

利用アプリが必要とする API と、CEF / wgpu / OS adapter が必要とする内部 API を同一にしない。

### 7.2 Panel と Surface を同一概念にしない

Panel は IDE UI 上の配置・表示単位、Surface は描画・入力・Lifecycle の接続境界とする。

Standard UI Panel は Surface を必要としない場合がある。

### 7.3 GPU Viewport と GPU Surface を同一概念にしない

Viewport は用途固有機能を提供でき、Surface は Dock 接続を担当する。

### 7.4 Surface output を CPU / GPU の一方へ固定しない

CEF OSR と wgpu の双方を不自然な copy / readback なしで扱える境界を設計する。

### 7.5 Input / IME を Browser 専用にしない

IME / Composition は共通入力モデルとし、Browser / GPU 等の adapter が各入力先へ変換する。

### 7.6 OS 固有 API を利用アプリへ要求しない

Windows / Linux / macOS 差異は Framework 内部へ閉じ込める。

### 7.7 Runtime ownership を利用アプリから奪わない

最初の利用アプリでは meridian-mujoco-runtime が MuJoCo simulation loop / RuntimeSession / domain state を所有する。

Framework は Runtime 固有の ownership を要求せず、表示・入力に必要な境界を提供する。これにより Framework が特定 Runtime の実行モデルへ依存することを避ける。

### 7.8 将来の Runtime 分離を阻害しない

v0.1.0 で Runtime process 分離を完成させないが、Surface / Viewport / Panel API が UI process 内の具体実装所有を過度に前提としないようにする。

## 8. Framework 利用アプリ実装手順

v0.1.0 の詳細設計は、最初の利用アプリである meridian-mujoco-runtime を Framework 利用アプリとして組み立てる手順から逆算する。

### Step 1. Framework をアプリへ導入する

利用アプリは Cargo dependency として workflow-ide-framework を導入する。

この段階の利用アプリには、egui / eframe / egui_dock / wgpu / CEF 等の Framework 内部 backend の初期化を要求しない。

Step 1 の最小ゴールは次とする。

> Framework dependency を追加し、Application を Framework へ渡すことで IDE Window を起動できる。

GUI Application の最上位 Lifecycle は Framework が所有し、利用アプリ固有 Runtime の Lifecycle は利用アプリが所有する。

```text
OS
 |
workflow-ide-framework
 |  Window / UI event loop / Dock / Panel lifecycle
 |  Surface infrastructure / OS input
 |
Application
 |  application state / application actions
 |
meridian-mujoco-runtime
    MuJoCo Runtime / simulation loop / RuntimeSession
    Robot / Field / Scenario / sysid / SIL / HIL
```

したがって Framework は MuJoCo simulation loop や RuntimeSession の所有者にならず、UI frame lifetime と Runtime execution lifetime を同一にしない。

この段階では具体的な公開 API 名・trait・型を確定しない。概念上は Application を Framework の起動境界へ渡せればよく、具体 API は後続 Step の要求を確認した後に決定する。

### Step 2. Application 基本設定

Framework 導入直後に、利用アプリ全体へ適用する基本設定を行う。

ここでは Panel や Runtime の実装詳細を扱わず、「Framework 利用アプリとして起動するための全体設定」だけを定義する。設定項目は **必須 / 任意 / Framework 既定値** に分け、利用アプリが backend 固有設定を知らなくても起動できることを優先する。

#### 2.1 必須設定

v0.1.0 では、原則として次だけを必須候補とする。

- Application ID
- Application 表示名

Application ID は内部識別、設定保存、将来の Workspace / Session 等で利用できる安定した識別子とする。表示名とは分離する。

#### 2.2 任意設定

利用アプリが必要な場合だけ指定する。

- 初期 Window title
- 初期 Window size
- 最小 Window size
- Custom Title Bar の利用方針
- Embedded Font の追加
- UI scale 等の表示設定
- Application icon
- Framework Action を配置する Toolbar / Menu 等の基本 UI 方針

具体的な設定型や項目名はこの段階では確定しない。

#### 2.3 Framework 既定値

指定がなければ Framework が安全な既定値を提供する。

- Window size
- Window position
- Native / Custom Title Bar の基本選択
- Framework 標準 Embedded Font
- Dock の基本外観
- Surface backend の選択
- OS ごとの差異吸収

CEF / wgpu / egui / eframe / Window backend の詳細設定は、通常の Application 基本設定には露出させない。

#### 2.4 設定の責務境界

Application 基本設定は静的または起動時に決まる構成を中心とする。

```text
Application basic configuration
  ├─ identity
  ├─ window
  ├─ appearance / font
  └─ framework-wide UI policy

Panel declaration        -> Step 3
Dock layout              -> Step 4
Panel implementation     -> Step 5
Runtime connection       -> Step 6
Run / Debug / Test       -> Step 7
```

アプリ固有 Runtime、MuJoCo、RobotDefinition、RuntimeSession 等の設定を Framework Application 設定へ混在させない。

#### 2.5 想定する利用形

具体 API は未確定だが、アプリ側からは概念的に一つの設定を渡せる形を目標とする。

```rust
ApplicationConfig {
    id: "...",
    name: "...",
    window: ...,
    appearance: ...,
}
```

Framework の詳細 API を知らなくても標準設定で起動でき、必要な項目だけ上書きできることを基本とする。

#### 2.6 Step 2 完了条件

- Application ID / 表示名だけで Framework の標準 Window を起動できる。
- Window / Font / Title Bar 等を必要に応じて上書きできる。
- backend 固有設定を利用アプリへ要求しない。
- Meridian 固有 Runtime 設定を Application 基本設定へ持ち込まない。
- 後続の Panel / Layout / Action 定義を追加できる設定境界がある。

### Step 3. Panel 宣言

Application 基本設定の次に、利用アプリが IDE 上で使用する Panel を宣言する。

この Step では Panel の具体的な描画処理や Runtime 接続はまだ実装しない。「どの Panel が存在し、それがどの種類の表示領域を必要とするか」を Framework へ登録する。

#### 3.1 Panel 宣言の基本単位

各 Panel は最低限、次の情報を持つ。

- Panel ID
- 表示名
- Panel kind
- 初期表示状態

Panel ID は Layout、状態保存、Action、将来の Workspace / Session 等から参照できる安定した識別子とする。表示名とは分離する。

#### 3.2 Panel kind

v0.1.0 では少なくとも次の種類を扱う。

- Standard UI Panel
- GPU Viewport Panel
- Browser Panel

```text
Panel
  ├─ Standard UI
  ├─ GPU Viewport
  └─ Browser
```

Panel kind は Framework が必要な表示・Surface infrastructure を選択するための分類であり、アプリ固有の用途名ではない。

例えば Meridian の `Simulation View` は GPU Viewport Panel、`Runtime Status` は Standard UI Panel として宣言できる。

#### 3.3 Meridian の初期 Panel 候補

最初の実利用では、仮に次を用意する。

```text
Meridian MuJoCo Runtime
  ├─ Simulation View    : GPU Viewport
  ├─ Runtime Control    : Standard UI
  ├─ Runtime Status     : Standard UI
  ├─ Log                : Standard UI
  └─ Help               : Browser (optional)
```

この一覧は v0.1.0 の固定 Panel セットではなく、Framework の Panel 宣言方法を検証するための最初の利用例とする。

#### 3.4 宣言と実装を分離する

Panel 宣言時には、MuJoCo 描画、Runtime 操作、Log 表示等の実装を要求しない。

```text
Step 3: declaration
Simulation View = GPU Viewport Panel
        |
Step 4: layout
        |
Step 5: implementation
        |
Step 6: Runtime connection
```

これにより Layout は Panel の内部実装を知らずに Panel ID を使って構成できる。

#### 3.5 Panel 固有設定

Panel kind ごとの最低限の静的設定は宣言へ含めてもよい。

例:

- Standard UI: 基本的には追加設定なし
- GPU Viewport: 初期表示方針、必要なら描画更新方針
- Browser: 初期 URL 等

ただし wgpu Device / Queue / Texture、CEF browser object 等の backend 固有型は Panel 宣言へ露出させない。

動的な処理、callback、Runtime state、描画コードは Step 5 / 6 で接続する。

#### 3.6 想定する利用形

具体 API は未確定だが、概念的には Application 設定へ Panel 宣言を追加できる形を想定する。

```rust
panels: [
    Panel {
        id: "simulation",
        name: "Simulation View",
        kind: GpuViewport,
    },
    Panel {
        id: "runtime-control",
        name: "Runtime Control",
        kind: StandardUi,
    },
    Panel {
        id: "runtime-status",
        name: "Runtime Status",
        kind: StandardUi,
    },
    Panel {
        id: "log",
        name: "Log",
        kind: StandardUi,
    },
]
```

これは API 確定案ではなく、利用アプリ側から見た必要情報を確認するための仮表現である。

#### 3.7 Framework が Panel 宣言から準備するもの

Panel kind に応じて Framework が必要な内部領域を準備する。

- Dock 上の Panel container
- Panel lifecycle
- Resize / Visibility / Focus の伝達
- GPU Viewport の Surface infrastructure
- Browser の Surface infrastructure
- 共通 input routing

アプリ側は Panel 宣言の段階でこれらを個別初期化しない。

#### 3.8 Step 3 完了条件

- アプリ側が Panel ID / 表示名 / kind を宣言できる。
- 複数 Panel を宣言できる。
- Panel 宣言だけでは内部実装や Runtime ownership を要求しない。
- Layout が Panel ID を参照できる。
- GPU / Browser backend 固有型をアプリの Panel 宣言へ要求しない。
- 後から Panel 実装と Runtime 接続を追加できる。

### Step 4. 初期 Layout 設定

宣言した Panel の初期 Dock Layout を設定する。

### Step 5. Panel 実装・カスタマイズ

Standard UI / GPU Viewport / Browser 等の各 Panel の内容を実装する。

### Step 6. Application / Runtime 接続

Panel とアプリ固有 State / Runtime を接続する。

### Step 7. Rust Action 実装・登録

Build / Run / Debug / Test およびアプリ固有処理を Rust Action として実装・登録する。

### Step 8. Framework 利用アプリとして実行・検証

Framework 全体として Build / Run / Debug / Test と integration acceptance を実施する。

## 9. v0.1.0 の実装順序

1. v0.1.0 公開 API の利用シナリオと ownership 境界を定義する。
2. Window / Dock / Panel の最小 Framework API を定義する。
3. Surface lifecycle / input / output の共通 API を定義する。
4. GPU Viewport / GPU Surface API を定義する。
5. Browser Panel / Browser Surface API を定義する。
6. Embedded Font / IME / caret location API を定義する。
7. P0 Probe のコードを Framework 実装へ移植・整理する。
8. Framework 内部の最小 integration example / probe を整備する。
9. meridian-mujoco-runtime の `develop` から Framework を利用する integration acceptance を実施する。
10. 結果を基に v0.1.0 公開 API を確定する。

## 10. v0.1.0 以降

v0.1.0 で「IDE の外枠 + Panel + Surface」が利用可能になった後、Event / State、Command、Runtime、Workflow、Plugin、GPU Viewport 高機能化等を v0.x 系で段階的に追加する。

v0.1.0 の API はこれらの完成形を先取りして過剰設計するのではなく、後から追加できる責務境界を確保することを優先する。
