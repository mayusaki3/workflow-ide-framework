# v0.1.0 開発概要

## 1. 位置付け

v0.1.0 は、Phase 0 の初期技術検証で個別に成立確認した要素を、実際に利用可能な Workflow IDE Framework の最小構成へ統合する最初の開発版である。

v0.1.0 の目的は「すべての IDE 機能を実装すること」ではない。

アプリケーション開発者が Framework を利用して、Dock 型 IDE の外枠を構築し、その中へ通常 UI、GPU Viewport、Browser Panel を同じ UI モデルの下で配置できる状態を作ることをゴールとする。

## 2. v0.1.0 のゴール

v0.1.0 完了時には、Framework 利用アプリから次の最小 IDE を構築できること。

```text
Application
   |
Workflow IDE Framework
   |
   +-- Window / Custom Title Bar
   +-- Dock / Panel
   |     +-- Standard UI Panel
   |     +-- GPU Viewport Panel
   |     +-- Browser Panel
   |
   +-- Surface
         +-- GPU Surface
         +-- Browser Surface
```

利用アプリは Windows / Linux / macOS の個別 Window API、CEF OSR、wgpu の Dock 接続処理を直接記述しない。

## 3. v0.1.0 でできるようにすること

### 3.1 IDE Window

- Framework から IDE Window を起動できる。
- Dock UI を表示できる。
- 必要な環境では Custom Title Bar を使用できる。
- Embedded Font により日本語 UI を表示できる。

### 3.2 Panel / Dock

- 利用アプリが Panel を定義できる。
- 複数 Panel を Dock 上へ配置できる。
- Panel の Resize が内容へ伝達される。
- 通常の egui UI を Panel 内容として表示できる。

v0.1.0 では「1 tab = 1 area」を前提としない。

### 3.3 GPU Viewport

- 利用アプリが GPU Viewport を Panel として配置できる。
- GPU Viewport の描画結果を GPU Surface 経由で Dock 内へ表示できる。
- Resize / Visibility / Focus / Lifecycle / 基本入力を扱える。
- MuJoCo、VRM Preview、Simulation 等を後続で実装できる境界を持つ。

v0.1.0 自体には MuJoCo や VRM のドメイン実装を含めない。

### 3.4 Browser Panel

- 利用アプリが Browser Panel を Dock 上へ配置できる。
- CEF OSR を Browser Surface の主実装として利用する。
- URL を読み込み、Dock 内で表示・更新できる。
- Pointer / Wheel / Keyboard / Focus / Text / IME を Browser へ渡せる。

Help / Docs / Tutorial / AI Chat 等の実アプリ機能そのものは v0.1.0 の必須成果物としない。

### 3.5 Surface 共通入力

GPU / Browser の双方で共通の入力モデルを利用できるようにする。

対象:

- PointerMove
- PointerButton
- Wheel
- Keyboard
- TextInput
- CompositionStart
- CompositionUpdate
- CompositionCommit
- CompositionEnd
- Focus

文字入力を行う Surface は caret / composition target の位置を Framework へ通知できる。

GPU Surface に IME を必須とはしない。GPU Viewport 内の独自 UI 等が文字入力を必要とするときに共通 IME model を利用できることをゴールとする。

### 3.6 日本語

- Framework renderer 内の日本語表示を Embedded Font で成立させる。
- OS font fallback のみに依存しない。
- Linux Native Window Title の問題を Framework 利用アプリへ露出させず、必要に応じて Custom Title Bar を利用できる。
- Browser Surface の日本語 IME を共通 Surface input model から CEF へ接続できる。
- GPU Viewport 内で文字入力を実装する場合にも同じ IME model を利用可能にする。

P0-2 で記録した Windows Browser Surface の最初の Space に関する Candidate Window 挙動は残課題として追跡する。

## 4. 最初の実利用アプリ

v0.1.0 の最初の実利用アプリは `mayusaki3/meridian-mujoco-runtime` の `develop` ブランチとする。

meridian-mujoco-runtime は MuJoCo を中核とするロボットシミュレーション Runtime であり、将来的に sysid、SIL / HIL、SimToReal / RealToSim、RuntimeSession、実時間 / simulation time 等を扱う。

workflow-ide-framework はこれらのドメイン機能を所有しない。Framework は、それらを IDE 上で表示・操作するための Window / Dock / Panel / Surface / Input の境界を提供する。

責務境界は次を基本とする。

```text
meridian-mujoco-runtime
  ├─ MuJoCo / simulation loop
  ├─ RuntimeSession
  ├─ Robot / Actuator / Field / Scenario
  ├─ sysid / SIL / HIL
  └─ domain state
          |
          | workflow-ide-framework public API
          v
workflow-ide-framework
  ├─ Window
  ├─ Dock / Panel
  ├─ Standard UI
  ├─ GPU Viewport / GPU Surface
  ├─ Browser Panel / Browser Surface
  └─ Input / IME / Lifecycle
```

MuJoCo API や meridian 固有データ型を workflow-ide-framework の公開 API に組み込まない。

### 4.1 利用イメージ

最初の実利用では、最低限次の構成を一つの IDE Window に同時表示できることを目標とする。

```text
+----------------------------------------------------+
| Custom / Native Title                              |
+----------------------+-----------------------------+
| Standard UI Panel    | GPU Viewport                |
|                      |                             |
| 日本語 UI             | dynamic GPU rendering       |
+----------------------+-----------------------------+
| Browser Panel                                      |
| URL display / pointer / keyboard / Japanese IME   |
+----------------------------------------------------+
```

Framework 内部には最小 example / probe を保持してよいが、v0.1.0 の実利用 Acceptance は meridian-mujoco-runtime から Framework を利用して成立することを基準とする。

meridian-mujoco-runtime 側が MuJoCo の simulation / render に必要な状態と更新タイミングを所有し、workflow-ide-framework は GPU Viewport の描画先、Dock 統合、入力、Resize / Visibility / Focus / Lifecycle を提供する構成を第一候補とする。

## 5. v0.1.0 の完了条件

v0.1.0 は以下を満たした時点で完了とする。

1. Framework crate の公開境界から Window / Dock / Panel を構築できる。
2. Standard UI Panel、GPU Viewport Panel、Browser Panel を同一 Window / Dock 内で共存させられる。
3. GPU / Browser が共通 Surface lifecycle / input model を利用する。
4. GPU Surface と Browser Surface の実装固有型を、不要に利用アプリ API へ露出させない。
5. Embedded Font による日本語 UI 表示が成立する。
6. Browser Panel で日本語 IME 入力が可能である。
7. GPU Viewport は共通 IME model を受け取れる設計・実装境界を持つ。実際の GPU 内文字編集 UI は acceptance application で最小確認する。
8. Resize / Visibility / Focus / Create / Close の基本 Lifecycle が Panel / Surface 間で成立する。
9. Windows で meridian-mujoco-runtime を最初の実利用アプリとした integration acceptance を完了する。
10. Linux は利用可能な VM で判定可能な項目を確認する。
11. Linux 実機 / 物理 GPU / macOS 等、環境を用意できない項目は `？` として記録し、非対応とは判定しない。
12. v0.1.0 の公開 API と内部 backend 境界が文書化されている。

## 6. v0.1.0 に含めないもの

以下は将来の v0.x へ送る。

- Workflow Node / Graph 実装
- Event / State 基盤の完成
- Command / Undo / Redo 基盤の完成
- Runtime process 分離
- Remote Runtime
- Plugin Loader / Plugin API
- Workspace / Session の完全な保存・復元
- 本格的な Layout persistence
- MuJoCo / VRM 等のドメイン固有 Viewport
- AI Runtime
- Debugger
- zero-copy / GPU 間 Texture 共有の最適化
- GPU backend ごとの性能最適化
- Accessibility / Drag and Drop / Clipboard の完全対応

ただし、将来追加するために必要な拡張点を v0.1.0 API が不必要に閉じないことは要求する。

## 7. API 設計へ与える制約

詳細 API は上記ゴールから逆算する。

### 7.1 Application API と Backend API を分離する

利用アプリが必要とする API と、CEF / wgpu / OS adapter が必要とする内部 API を同一にしない。

### 7.2 Panel と Surface を同一概念にしない

Panel は IDE UI 上の配置・表示単位、Surface は描画・入力・Lifecycle の接続境界とする。

Standard UI Panel は Surface を必要としない場合がある。

### 7.3 GPU Viewport と GPU Surface を同一概念にしない

Viewport は用途固有機能を提供でき、Surface は Dock 接続を担当する。

### 7.4 Surface output を CPU / GPU の一方へ固定しない

CEF OSR と wgpu の双方を不自然な copy / readback なしで扱える境界を設計する。

### 7.5 Input / IME を Browser 専用にしない

IME / Composition は共通入力モデルとし、Browser / GPU 等の adapter が各入力先へ変換する。

### 7.6 OS 固有 API を利用アプリへ要求しない

Windows / Linux / macOS 差異は Framework 内部へ閉じ込める。

### 7.7 Runtime ownership を利用アプリから奪わない

最初の利用アプリでは meridian-mujoco-runtime が MuJoCo simulation loop / RuntimeSession / domain state を所有する。

Framework は Runtime 固有の ownership を要求せず、表示・入力に必要な境界を提供する。これにより Framework が特定 Runtime の実行モデルへ依存することを避ける。

### 7.8 将来の Runtime 分離を阻害しない

v0.1.0 で Runtime process 分離を完成させないが、Surface / Viewport / Panel API が UI process 内の具体実装所有を過度に前提としないようにする。

## 8. Framework 利用アプリ実装手順

v0.1.0 の詳細設計は、最初の利用アプリである meridian-mujoco-runtime を Framework 利用アプリとして組み立てる手順から逆算する。

### 検証の反復性

各 Step は **Framework 側と利用アプリ側の二系統で build / run を検証する**。

```text
Framework repository
  Framework + Framework sample
       ↓
  build / run / Step verification

Consumer repository
  Framework + consumer application
       ↓
  build / run / Step verification
```

最初の利用アプリでは Consumer = meridian-mujoco-runtime とする。

Framework 側の sample は、その Step の Framework 機能だけを最小条件で確認する基準実装とする。Meridian 側では同じ Step が実アプリへの導入条件でも成立することを確認する。したがって、Framework sample の成功だけでも Meridian の成功だけでも、その Step の検証完了とはしない。

この二系統検証は Step 1 だけでなく、Step 2、3、4、および Step 5 以降にも継続して適用する。Framework sample は Framework 自身の各バージョンで継続する固定の基準検証系とし、Consumer はバージョンごとに選定する実プロジェクトとする。例えば v0.1.0 では meridian-mujoco-runtime を使用するが、v0.2.0 以降は別プロジェクトへ変更してよい。

Step 1〜4 の利用手順は累積状態だけで検証しない。各 Step の検証時には利用アプリを Framework 適用前の基準状態へ戻し、Step 1 から対象 Step までを再適用して成立することを確認する。

これにより、開発途中の残存状態や未記録の手作業へ依存せず、第三者が同じ導入手順を再現できることを要求する。

この反復検証は Step 4.5 の外部環境検証にも継続し、Framework側Probe / Standard Panelの検証結果とConsumer側利用結果を混同しない。

### Step 5. Panel 実装・カスタマイズ

Standard UI / GPU Viewport / Browser 等の各 Panel の内容を実装する。

Step 4.6 Localization / Language Switching完了後、Step 5ではPanel宣言とPanel実装を接続する公開境界を定義する。

基本方針:

- Rustでは継承を前提とせず、FrameworkがPanel契約を提供し、Applicationが実装を登録する。
- `PanelDefinition` はID / 表示名 / kind / 初期表示等の宣言情報として維持する。
- Panel実装は宣言とは別に登録し、Application固有State / RuntimeのownershipをFrameworkへ強制移譲しない。
- Framework Standard PanelとApplication / Consumer Panelを区別する。
- Framework Standard Panelも原則としてConsumer Panelと同じ公開Panel API上で実装し、Framework内部専用の別系統Panel APIを増やさない。
- Logging Settings / Language SettingsはFramework Standard Panelとして整理する。
- WFIDE ProbeはFramework maintenance専用であり、通常Consumerへ同梱しない。
- Standard UI Panelはegui UI実装を接続できる。
- GPU Viewport PanelはGPU Surfaceとの接続境界を持つが、Applicationへwgpu backend固有型を不要に露出しない。
- Browser PanelはBrowser Surfaceとの接続境界を持つが、ApplicationへCEF固有型を不要に露出しない。
- Panel描画frameとMeridian等のRuntime / simulation loopの更新周期を同一視しない。
- Frameworkは表示・編集の汎用機構を提供するが、MuJoCo / Robot / Runtime等のConsumer domain semanticsは持たない。

#### Step 5 Standard Panel方針

v0.1.0で実装するFramework Standard Panel:

- Text Editor
- Log Viewer

将来のFramework Standard Panel候補として、Step 5 API設計時に同じ仕組みで実装可能なことを考慮する:

- File Explorer
- Properties / Inspector
- Output
- Problems
- Help / Browser
- Settings
- Terminal
- Search
- Outline
- Data / Table Viewer
- Plot / Chart Viewer

Data / Table Viewerは時系列値、計測値、simulation値等をdomain非依存のTableModelとして扱える構造とし、Probe結果の表形式表示にも利用する。このためStep 5で早期実装する。Plot / Chart Viewerはseries / time-series等をdomain非依存に可視化する構造を想定し、v0.1.0 Step 5の実装必須範囲には含めない。

Text Editorは編集UI / cursor / selection / modified / read-only等をFrameworkが担当し、load / save / validationやMJCF / URDF等の意味はDocument Provider / Consumer側へ分離する。

Log ViewerはWFIDE Logging Coreのviewerとし、LoggingのownershipをPanelへ移さない。将来はstructured fieldを任意fieldでfilter / displayできる余地を確保する。

#### Step 5 Consumer Panel / Application境界

Meridian検証ではConsumer Panelを単に表示できるだけでなく、Panel間を直接結合せずに次の最小経路を成立させる。

```text
Runtime Control
    ↓ user action
Application state / event boundary
    ↓ state update
Runtime Status
```

Step 5.1の公開境界では少なくとも以下を扱える拡張余地を確保する。

- Panel render context
- Application state access
- Event / Action request
- Panel identity

ここで本格的なEvent Dispatcher / Command / Undo / RedoをStep 5へ前倒ししない。Step 5では後続のStep 6 Runtime接続、Step 7 Rust Action、および将来のEvent / State / Command基盤へ発展できる最小境界を検証する。

Meridian固有のSimulation View / Runtime Control / Runtime Statusおよび将来のRobot / Simulation / Dataset / sysid / SIL / HIL関連UIはConsumer責務とする。Standard Inspector / Table / Plot等へMeridian modelを渡して利用できる構造を優先し、Framework側へMeridian domain型を導入しない。

#### Step 5 実装順序

1. Step 5.1 Standard UI Panel API
2. Step 5.2 Framework Standard Panel基盤
3. Step 5.3 Data / Table Viewer
4. Step 5.4 ProbeのData / Table Viewer移行
5. Step 5.5 Text Editor
#### Step 5.5 Text Editor検証要件

Text Editor SampleにはLanguage Settingsを併設し、Framework Standard Panelのruntime localizationを同一Sample内で確認する。

検証対象:

- Text EditorがplaceholderではなくDock内で編集可能
- 編集時にmodified表示が付く
- Save / 保存ラベルがlocale切替へ追従
- Embedded Fontで日本語文書を表示可能
- Text EditorがPanelの利用可能な縦領域を使用する
- status barをDock Panel内部の最下部に固定し、Panel外へ描画しない
- status barにcursorの行 / 列、文字コード、language hintを表示
- UTF-8 / Shift_JIS等のencoding metadataをDocument側で保持可能
- Windows IME候補位置が入力caretへ追従すること

Text Editorのcode editorはApplication FontをMonospace familyにも登録し、日本語glyphを表示できる構成とする。

Text Editor layoutのWindows確認では、以下の3件を確認しており、Status Bar / Editor layoutは○としない。

- TextEdit下端がStatus Bar直上で停止しない
- Status BarがPanel最下端を維持せず、Editor contentとともにスクロールする
- TextEditとStatus Barが重なる

最初のexplicit rect方式でも解消しなかったため、Text Editor専用child UIをDockのavailable rectに固定し、その内部でToolbar / Status BarをTopBottomPanelの兄弟領域として先に予約し、CentralPanelへEditorだけを配置する方式へ変更した。Status BarをEditorのcontent / scroll extentから分離する。再検証待ち。

### Step 5.5 IME候補位置 原因特定メモ

Windows右端入力の実測では `IMEOutput.cursor_rect.min.x ≈ 896.6` に対し、候補ウィンドウはText Editor左端付近へ表示された。raw winitの `set_ime_cursor_area` はWindows/Linux VMとも追従する。

egui-winitのPlatformOutput処理経路をソース確認したところ、IME候補位置の `set_ime_cursor_area` に `IMEOutput.cursor_rect` ではなく `IMEOutput.rect` を使用する実装が確認された。 `rect` はTextEdit全体の矩形、`cursor_rect` は主カーソル矩形である。この実装なら候補がTextEdit左端へ固定される今回の観測と整合する。

現時点ではWFIDE側の固定offset補正は行わない。直接依存のegui-winit診断Probeを追加し、使用中の0.34.2系でAPI/挙動を再確認したうえで、upstream修正またはFramework側の限定的workaroundを判断する。


#### Step 5.5 IME候補位置: cursor_rect診断結果

Windows実機で、完全な egui-winit 0.34.3 を基に `handle_platform_output()` のIME候補領域を `ime.rect` から `ime.cursor_rect` へ変更した診断版を実行した。右側の入力カーソル（画面内診断値: caret≈670.7,196.0 / ime≈669.3,194.5 / send≈669.3,194.5,3.0,22.0）に対し、Windows IME候補ウィンドウが入力位置直下へ追従することをスクリーンショットで確認した。

- Windows: `ime.cursor_rect` 使用時の候補追従 ○
- Linux VM: 修正版は未検証 ？
- macOS: ？

#### Step 5.5 IME候補位置: upstream調査と正式対応方針

upstreamを確認した。egui issue #7906 はPR #7983に関連付けられてcloseされ、PR #7983はmerge済みだが、主内容はIME event ownership/composition処理の再構成であり、候補位置用矩形を `IMEOutput.cursor_rect` に変更する修正ではない。最新安定版として確認した egui-winit 0.36.2 でも `handle_platform_output()` は `let ime_rect_px = pixels_per_point * ime.rect;` のままである。

したがって、単純なegui更新では今回の候補位置問題は解消しない。WFIDE v0.1.0では、検証済み0.34.3を維持しつつ、完全なupstream egui-winit 0.34.3に対して `ime.rect -> ime.cursor_rect` の最小差分を適用する依存patchを正式な暫定対応とする。Windows実機 ○ / Linux VM Wayland+IBus+mozc-jp ○ / macOS ？。固定座標offset補正は採用しない。

今後upstreamで同等修正がreleaseされた場合はpatchを除去し、通常依存へ戻してWindows/Linux VM/macOSの検証表を更新する。
