# v0.1.0 開発概要

## 1. 位置付け

v0.1.0 は、Phase 0 の初期技術検証で個別に成立確認した要素を、実際に利用可能な Workflow IDE Framework の最小構成へ統合する最初の開発版である。

v0.1.0 の目的は「すべての IDE 機能を実装すること」ではない。

アプリケーション開発者が Framework を利用して、Dock 型 IDE の外枠を構築し、その中へ通常 UI、GPU Viewport、Browser Panel を同じ UI モデルの下で配置できる状態を作ることをゴールとする。

## 2. v0.1.0 のゴール

v0.1.0 完了時には、Framework 利用アプリから次の最小 IDE を構築できること。

```text
Application
   |
Workflow IDE Framework
   |
   +-- Window / Custom Title Bar
   +-- Dock / Panel
   |     +-- Standard UI Panel
   |     +-- GPU Viewport Panel
   |     +-- Browser Panel
   |
   +-- Surface
         +-- GPU Surface
         +-- Browser Surface
```

利用アプリは Windows / Linux / macOS の個別 Window API、CEF OSR、wgpu の Dock 接続処理を直接記述しない。

## 3. v0.1.0 でできるようにすること

### 3.1 IDE Window

- Framework から IDE Window を起動できる。
- Dock UI を表示できる。
- 必要な環境では Custom Title Bar を使用できる。
- Embedded Font により日本語 UI を表示できる。

### 3.2 Panel / Dock

- 利用アプリが Panel を定義できる。
- 複数 Panel を Dock 上へ配置できる。
- Panel の Resize が内容へ伝達される。
- 通常の egui UI を Panel 内容として表示できる。

v0.1.0 では「1 tab = 1 area」を前提としない。

### 3.3 GPU Viewport

- 利用アプリが GPU Viewport を Panel として配置できる。
- GPU Viewport の描画結果を GPU Surface 経由で Dock 内へ表示できる。
- Resize / Visibility / Focus / Lifecycle / 基本入力を扱える。
- MuJoCo、VRM Preview、Simulation 等を後続で実装できる境界を持つ。

v0.1.0 自体には MuJoCo や VRM のドメイン実装を含めない。

### 3.4 Browser Panel

- 利用アプリが Browser Panel を Dock 上へ配置できる。
- CEF OSR を Browser Surface の主実装として利用する。
- URL を読み込み、Dock 内で表示・更新できる。
- Pointer / Wheel / Keyboard / Focus / Text / IME を Browser へ渡せる。

Help / Docs / Tutorial / AI Chat 等の実アプリ機能そのものは v0.1.0 の必須成果物としない。

### 3.5 Surface 共通入力

GPU / Browser の双方で共通の入力モデルを利用できるようにする。

対象:

- PointerMove
- PointerButton
- Wheel
- Keyboard
- TextInput
- CompositionStart
- CompositionUpdate
- CompositionCommit
- CompositionEnd
- Focus

文字入力を行う Surface は caret / composition target の位置を Framework へ通知できる。

GPU Surface に IME を必須とはしない。GPU Viewport 内の独自 UI 等が文字入力を必要とするときに共通 IME model を利用できることをゴールとする。

### 3.6 日本語

- Framework renderer 内の日本語表示を Embedded Font で成立させる。
- OS font fallback のみに依存しない。
- Linux Native Window Title の問題を Framework 利用アプリへ露出させず、必要に応じて Custom Title Bar を利用できる。
- Browser Surface の日本語 IME を共通 Surface input model から CEF へ接続できる。
- GPU Viewport 内で文字入力を実装する場合にも同じ IME model を利用可能にする。

P0-2 で記録した Windows Browser Surface の最初の Space に関する Candidate Window 挙動は残課題として追跡する。

## 4. v0.1.0 の利用イメージ

v0.1.0 の受け入れ確認用アプリでは、最低限次の構成を一つの IDE Window に同時表示できることを目標とする。

```text
+----------------------------------------------------+
| Custom / Native Title                              |
+----------------------+-----------------------------+
| Standard UI Panel    | GPU Viewport                |
|                      |                             |
| 日本語 UI             | dynamic GPU rendering       |
+----------------------+-----------------------------+
| Browser Panel                                      |
| URL display / pointer / keyboard / Japanese IME   |
+----------------------------------------------------+
```

このアプリは製品 IDE ではなく、Framework API を外部利用者の立場から確認する integration example / acceptance application とする。

## 5. v0.1.0 の完了条件

v0.1.0 は以下を満たした時点で完了とする。

1. Framework crate の公開境界から Window / Dock / Panel を構築できる。
2. Standard UI Panel、GPU Viewport Panel、Browser Panel を同一 Window / Dock 内で共存させられる。
3. GPU / Browser が共通 Surface lifecycle / input model を利用する。
4. GPU Surface と Browser Surface の実装固有型を、不要に利用アプリ API へ露出させない。
5. Embedded Font による日本語 UI 表示が成立する。
6. Browser Panel で日本語 IME 入力が可能である。
7. GPU Viewport は共通 IME model を受け取れる設計・実装境界を持つ。実際の GPU 内文字編集 UI は acceptance application で最小確認する。
8. Resize / Visibility / Focus / Create / Close の基本 Lifecycle が Panel / Surface 間で成立する。
9. Windows で integration acceptance を完了する。
10. Linux は利用可能な VM で判定可能な項目を確認する。
11. Linux 実機 / 物理 GPU / macOS 等、環境を用意できない項目は `？` として記録し、非対応とは判定しない。
12. v0.1.0 の公開 API と内部 backend 境界が文書化されている。

## 6. v0.1.0 に含めないもの

以下は将来の v0.x へ送る。

- Workflow Node / Graph 実装
- Event / State 基盤の完成
- Command / Undo / Redo 基盤の完成
- Runtime process 分離
- Remote Runtime
- Plugin Loader / Plugin API
- Workspace / Session の完全な保存・復元
- 本格的な Layout persistence
- MuJoCo / VRM 等のドメイン固有 Viewport
- AI Runtime
- Debugger
- zero-copy / GPU 間 Texture 共有の最適化
- GPU backend ごとの性能最適化
- Accessibility / Drag and Drop / Clipboard の完全対応

ただし、将来追加するために必要な拡張点を v0.1.0 API が不必要に閉じないことは要求する。

## 7. API 設計へ与える制約

詳細 API は上記ゴールから逆算する。

### 7.1 Application API と Backend API を分離する

利用アプリが必要とする API と、CEF / wgpu / OS adapter が必要とする内部 API を同一にしない。

### 7.2 Panel と Surface を同一概念にしない

Panel は IDE UI 上の配置・表示単位、Surface は描画・入力・Lifecycle の接続境界とする。

Standard UI Panel は Surface を必要としない場合がある。

### 7.3 GPU Viewport と GPU Surface を同一概念にしない

Viewport は用途固有機能を提供でき、Surface は Dock 接続を担当する。

### 7.4 Surface output を CPU / GPU の一方へ固定しない

CEF OSR と wgpu の双方を不自然な copy / readback なしで扱える境界を設計する。

### 7.5 Input / IME を Browser 専用にしない

IME / Composition は共通入力モデルとし、Browser / GPU 等の adapter が各入力先へ変換する。

### 7.6 OS 固有 API を利用アプリへ要求しない

Windows / Linux / macOS 差異は Framework 内部へ閉じ込める。

### 7.7 将来の Runtime 分離を阻害しない

v0.1.0 で Runtime process 分離を完成させないが、Surface / Viewport / Panel API が UI process 内の具体実装所有を過度に前提としないようにする。

## 8. v0.1.0 の実装順序

1. v0.1.0 公開 API の利用シナリオと ownership 境界を定義する。
2. Window / Dock / Panel の最小 Framework API を定義する。
3. Surface lifecycle / input / output の共通 API を定義する。
4. GPU Viewport / GPU Surface API を定義する。
5. Browser Panel / Browser Surface API を定義する。
6. Embedded Font / IME / caret location API を定義する。
7. P0 Probe のコードを Framework 実装へ移植・整理する。
8. integration acceptance application を作成する。
9. Windows / Linux VM で acceptance を実施する。
10. 結果を基に v0.1.0 公開 API を確定する。

## 9. v0.1.0 以降

v0.1.0 で「IDE の外枠 + Panel + Surface」が利用可能になった後、Event / State、Command、Runtime、Workflow、Plugin、GPU Viewport 高機能化等を v0.x 系で段階的に追加する。

v0.1.0 の API はこれらの完成形を先取りして過剰設計するのではなく、後から追加できる責務境界を確保することを優先する。
