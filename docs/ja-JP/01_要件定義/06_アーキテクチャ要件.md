# アーキテクチャ要件

Workflow IDE Framework “Kairi” のアーキテクチャは、以下の要件を満たすこと。

# 1. アプリケーション / プロジェクト構造

## 1.1 組み込み型構造

Kairiは独立したIDE製品ではなく、利用アプリケーションへ組み込んで使用できる構造とすること。

利用アプリケーション固有機能はKairi本体から分離できること。

## 1.2 プロジェクト責務の分離

Kairiが管理するプロジェクト共通情報と、利用アプリケーションが管理するプロジェクト固有データの責務を分離すること。

両者を一つのプロジェクトとして保存・復元できること。

## 1.3 イベントと状態

アプリケーションおよびプロジェクトのライフサイクルを、利用アプリケーションがイベントとして受け取れる構造とすること。

実行中に更新される状態は、必要な利用者が共有して参照・更新できる構造とすること。

## 1.4 オフライン利用

Kairiの基本機能は、外部サービスへの常時接続を必須とせず利用できる構造とすること。

# 2. ワークスペース / パネル構造

## 2.1 ワークスペースとパネルの分離

ワークスペースはパネルの配置とレイアウトを管理し、パネル自体は利用アプリケーションまたはKairiが所有する構造とすること。

同一パネルをワークスペース固有の実装へ固定しないこと。

## 2.2 複数パネル構成

利用アプリケーションの機能を単一画面へ固定せず、複数のパネルとして構成できること。

パネルはドッキング、表示・非表示等の配置状態を扱えること。

# 3. リソース / 共通サービス構造

## 3.1 リソース責務の分離

アプリケーションリソース、プロジェクトリソース、外部リソースを区別し、それぞれの所有範囲を維持できること。

## 3.2 疎結合構造

リソース管理、通知、ログ、多言語対応、テーマ等の共通サービスは、特定の利用アプリケーション固有機能へ依存しない構造とすること。

## 3.3 コマンド統一

利用アプリケーションの操作は、メニュー等の個別ユーザーインターフェースへ直接固定せず、共通のコマンドとして登録・実行できる構造とすること。

## 3.4 拡張可能な境界

将来機能を追加する際に、既存の利用アプリケーションへ不必要な変更を要求しない公開境界を維持すること。

# 4. 開発 / 実行環境

## 4.1 対象OSとOS依存性

Windows、Linux、macOSを動作対象とすること。

OS固有処理は可能な限りKairi内部へ閉じ込め、利用アプリケーションがOSごとの実装を持つことを基本要件としないこと。
